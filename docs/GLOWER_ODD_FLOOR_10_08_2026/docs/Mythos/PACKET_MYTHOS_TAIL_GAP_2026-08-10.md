## Главное: разрыв, который меняет постановку

Yoshida [33] скачан владельцем (Project Euclid, Uni-доступ) и прочитан. Его цепочка
доведена до числа для нашей ячейки — `phase4_scripts/yoshida_analytic_N.py`.

**Перекрёстная проверка сошлась:** `C₂(a₀) = |{(p,m) : p^m ≤ 13}| = 9`, список
`2,3,4,5,7,8,9,11,13` — ровно наш `PRIME_POWERS`.

**А константа — нет:**

```
поле ℚ: r₁ = 1, r₂ = 0, log A_k = 0,  a₀ = log√13
C₁(a₀) = 4·sinh(a₀)/a₀ = 5.19027975
порог:   C > μ + C₁ + 2·C₂ = 24.19027975
t₀ ≈ 1.7419251e+11        C₃ ≈ 4.6470562e+34
N > 1.5488372e+34
```

| | значение | статус |
|---|---|---|
| порог нашего сертификата головы | `R = 70` | **измерен** |
| порог, с которого коэрцитивность **доказана** | `~1.5e34` | следует из Lemma 3 |

Механизм раздувания: `Re ψ(σ+it) ~ log|t|`, значит `t₀ ~ e^C`, и `t₀` входит в `C₃`
кубически. При `C ≈ 24`, где `2·C₂ = 18` даёт основной вклад, получается масштаб `e^{72}`.
Оптимизация по `C` (оптимум при запасе `1/3`) — разы, не порядки.

### Вопрос к тебе — разведка, а не судейство

**Существует ли в литературе механизм коэрцитивности high-mode хвоста Weil/screw-формы с
константами, пригодными для практики** — то есть дающий порог порядка сотни, а не `10³⁴`?

Что интересует конкретно:

1. Работы **после** Yoshida 1992, где та же finite-codimension коэрцитивность получена с
   явными или хотя бы полиномиальными константами.
2. Обходы условия `Re ψ ≥ C`: оно и есть источник экспоненты. Есть ли формулировки, где
   архимедов вклад оценивается без выхода на `t₀ ~ e^C`?
3. Не платит ли кто-нибудь за это иначе — например, через локализацию по простым или
   через weighted-норму, где `2·C₂` не входит в порог аддитивно.

Если ответ «такого нет» — это тоже результат, и он переводит `Lock B` в разряд
собственной теоремы, а не извлечения из чужой.

## Три вещи для твоего ledger-скрипта поверх `glower_corrected_head.py`

**1. Грабли, на которые мы уже наступили — порядок инициализации.**

`c₀` обязана вычисляться **после** установки `ctx.dps`. Посчитанная раньше, она несёт
радиус дефолтных 15 знаков (`~1e-73` при `c₀ = 1e-58`), и `LDL^T` без пивотирования
раздувает его до `1e-3` к 22-му шагу — сертификат ложно падает в `INSUFFICIENT_PRECISION`.

Признак именно этой болезни, а не нехватки разрядов: **интервал не сужается при росте
точности**. У нас он не сузился со 120 до 300 знаков — это и выдало подделку. После
починки `‖R_c‖` упала с `8.97e-74` до `7.49e-285`.

**2. Матрицу не строить заново.** `CCMArbBuilder` импортируется из
`phase1_scripts/ccm_control_cell_penalty.py`, а не копируется. Так расхождение формул с
сертификатом Phase 1 невозможно по построению, а не по проверке.

**3. Что уже посчитано, чтобы не дублировать:**

```
Вход 1   R(μ=1) = 70          устойчиво N = 90…480; пивот хвоста застыл до 40-й цифры

         темп −0.980 %, −1.451 %, −1.328 % — перестал расти
         PASS = Q₁₃^odd ⪰ c₀I на срезе (c₀ внутри A_c, D_c)
         штраф d⁻¹‖R_c‖² ≤ 5.61e-569 — пренебрежим
```

Re-representation 1 исполнена в точном виде: `Y` есть решение `D_c Y = −E`, поэтому `R_c`
обнуляется до `7.49e-285`. Если ledger нужен для дискриминатора нуль-содержащего
интервала — этот случай у нас не наступил, интервал далёк от нуля.

**Чего ledger НЕ должен делать:** экстраполировать по `N`, применять Эйткена, считать

## 2. Мэппинг входного дизайна на существующее

| Роль из дизайна «Discovery Loop» | Наша реализация | Полнота |
|---|---|---|
| Тополог (глобальный DAG, Reverse-Math каркас, отсечение тупиков) | Мифос + крыша-опоры-канаты + `brief.py`/`cheap.py` + assembly-шаги в knowledge.db + LEDGER CLOSES/OPENS | [ЕСТЬ] |
| Археолог (семантический поиск изоморфизмов по структурным паттернам) | частично: litreview-конвейер + acquisition-такты петли; принцип «scan BY SIGNATURE, not by field» уже в K4/K9 | [ДЫРА] нет постоянного радара |
| Кузнец иголок (аналогия → локальный инструмент, ровно одно препятствие) | процесс минтования карт (пример: C13, 2026-08-23) + K8 jump-target («minimal missing identity») | [ЕСТЬ], ручной |
| Инквизитор (toy models, фазовый аудит, zero-circle, anti-hallucination) | Прошка: обязательные планты в каждом вердикте, аудит конвенций/знаков, K5 circularity, verifier-теги, «квитанции себе не выписывать» | [ЕСТЬ], строже дизайна |
| Полка знаний (data contract) | knowledge.db + ask.sh/СТЫКОВКИ + Lean-DAG | [ЕСТЬ] |

Паспорт «иголки» ↔ наша карта: NEEDLE_ID=card-ID; CROSS_DOMAIN_BRIDGE=src+MECHANISM;
P(K)=SIGNATURE; DEPENDENCY_FOOTPRINT≈CLOSES/OPENS; STATUS=STATUS.
Отсутствуют два поля: TOY_VALIDATION и явный DEPENDENCY_FOOTPRINT в самой
карте (сегодня они живут в вердиктах/records, не в колоде) — см. R1.

Протокол авто-пополнения из дизайна ↔ NAMEWATCH-конвейер, ратифицированный
вердиктом 2026-08-05: кандидат в карту требует ≥2 различных голов, ≥2 различных
фронтов, проверку покрытия существующими картами, shape-дискриминатор,
ратификацию владельца. Статус: РАТИФИЦИРОВАН, НЕ МАТЕРИАЛИЗОВАН. Ручной прогон
выполнен один раз (C13). Не изобретать заново — материализовать одобренное.

## 3. Операторный словарь (Гильберт–Пойя ↔ Route B)

Зачем: правильные поисковые сигнатуры для Археолога и язык для статьи.
Поиск по «compact resolvent + dilation generator + trace formula defect»
находит литературу, которую «Riemann Hypothesis» не найдёт.

| Их язык | Наш объект | Статус |
|---|---|---|
| Оператор Гильберта–Пойи Ĥ | A_λ Конна, формула (16); конечный уровень: `ccmWeilMatFinite` | конечный — kernel-checked; оконный — см. ниже |
| Импульс Берри–Китинга (H = xp, генератор дилатаций) | наш D = `ccmModeDiagFinite` в лог-координате (D ≅ (L/2πi)∂_t) | kernel-checked |
| Уравнение движения / коммутатор [H, генератор] | Γ = D·r; rank-two [M, D] = η⊗β − β⊗η | kernel-checked (3B) |
| Нётеровская аномалия масштабной симметрии | β-вектор (симметрия сломана краями окна и простыми) | язык; объекты kernel-checked |
| Периодические орбиты, период T, кратность k | prime-блок: Λ(p^k), период log p, кратность k | kernel-checked (pairing identity) |
| Формула следа Гуцвиллера | source-Weil форма W02 − WR − Prime | kernel-checked на finite span |
| Модулярная инверсия τ → −1/τ | u → 1/u; supplier T2 (inversion covariance окна) | OPEN |
| Poisson как источник модулярности | identity (18) Конна; BV Poisson-defect identity (3C.1.7); карта C13 | выведена (external classical inputs) |
| Невырожденность основного состояния | стена H2A SIMPLE_EVEN | OPEN — главная гипотеза |
| Нули на прямой | Theorem 6.1 Конна = линия Theorem 5.10 (H2b) | условный порт |
| Предел к Ξ (Гурвиц) | стена C3-B | OPEN |

Оконный Ĥ_λ формально: самосопряжённый оператор, представляющий замкнутую
полуограниченную форму `sourceWeilShiftedExtendedQuadraticForm` − сдвиг
(Като/Фридрихс). Замкнутость и нижняя граница — на диске; не хватает одного
гола «representation theorem». W9-предупреждение: гол закрывает вывеску, не
стену; RH-содержание — в спектральных свойствах (H2A/H2b/C3-B), которые
петля и грызёт.

## 6. Дополнение 2026-08-23 (вечер): типизация мостов и статусная машина

Источник: продолжение дизайн-диалога владельца (Gemini). Три элемента приняты
в план, с ремонтами.

**6.1. BRIDGE_KIND — типизация кросс-доменных мостов [ПЛАН, поле формата].**
Каждый мост между областями обязан носить тип:

```text
EXACT_ISOMORPHISM   — двусторонняя identity с доказанным crosswalk
FORM_IDENTITY       — тождество форм/функционалов на именованном домене
ONE_WAY_TRANSFER    — перенос механизма без обратного утверждения
HEURISTIC_PARALLEL  — словарь без теоремы (только для поисковых сигнатур)
```

У нас это уже живёт неявно: C04 SAME-COORDINATES-TWO-LAWS — запрет
неявного EXACT_ISOMORPHISM; пример ночи: «Гуцвиллер = наша форма» имеет тип
FORM_IDENTITY на finite span (QW_λ(f,f) = ⟨A_λf,f⟩ — paper), а «изометрия =
поточечный Фурье» была ABSENT и стала W1-маршрутом. Внедрение: поле в
карты арсенала и в CROSS_DOMAIN-записи дигестов (вместе с R1).

**6.2. Статусная машина инсайта [ПЛАН, имена для существующего].**

```text
GAP_LOCKED → CROSSWALK_TYPED → FALSIFIER_PASSED → KERNEL_VERIFIED
```

Фактически конвейер уже работает так (пример — ход C13 за одну ночь:
инсайт из чата → typed identity 3C.1.7 → планты/ремонты вердиктов →
ожидает Lean), не хватало только имён состояний. Внедрение: статусная
строка в паспорте карты (R1) и в supplier-леджерах. Гарантия та же, что
сформулирована в диалоге: случайный инсайт либо за минуту разбивается о
дискриминатор, либо встаёт на полку типизированным — висячих зависимостей
не бывает (наш NEXT_AFTER_SEMANTIC_ADMISSION_ONLY — тот же механизм на
уровне тактов).

## 7. Дополнение 2026-08-23 (ночь): почему type-directed search «не заработал сам» и лестница T1–T4

Замысел владельца (типизированные I/O-порты у каждого математического
объекта; meet-in-the-middle между стенами; отсечение 99.99% путей на
сигнатурах) — диагноз, почему текущая система реализует его лишь частично:

1. **Порты типизированы именами, не типами.** Каталог requires/provides
   хранит имена supplier'ов; carrier/нормировка/кванторы/метод суммирования
   не проверяются машиной. Ночь 3C.1.1–3C.1.9 — готовый каталог недостающих
   типов: SUMMATION_METHOD (tsum ≠ условная сумма), TRANSFORM_OBJECT
   (изометрия ≠ поточечный Фурье), REPRESENTATIVE (full-endpoint ≠
   midpoint), TOPOLOGY (Hilbert-плотность ≠ form core). Каждый —
   пойманный вручную C04-ремонт, отсекаемый type-check'ом на сигнатуре.
2. **Провода часто не существуют в природе.** Разрыв обычно «модуля нет ни
   у кого», не «маршрут не найден»: типовой поиск сжимает пространство до
   правильного вопроса, но модуль строится руками.
3. **Взрыв вариантов убит судьёй, не типами.** Плата — латентность
   вердикта; типизация переместит работу судьи с объектных подмен на
   математику.
4. **Каталог фрагментирован синонимами** (источник W9) и не сверяется с
   ядром (comparator-gap).

Существующие компоненты замысла: измеритель гэпов = `cheap.py` +
`CHAIN_GAP_DESIGN.md`; каталог микросхем = capability catalog (СТЫКОВКИ);
consumer-first маршрутизация = дисциплина судьи.

**Лестница внедрения (все ступени = V1-модули мандата AMDL; вход — V0):**

```text
T1: типовые поля в capability-записях (CARRIER/DOMAIN/NORMALIZATION/
    QUANTIFIERS/SUMMATION_METHOD/REPRESENTATIVE) — схема готова:
    AtomicInvariantContract v1 из мандата 179285ee.
T2: type-check на стыковке ask.sh: MISMATCH-строка + требуемый адаптер
    (прообраз: «type and sign table» Test 1 отчёта 3C.1.7).
T3: вторая координата в cheap.py — типовой разрыв рядом с ценой.
T4: двунаправленный meet-in-the-middle по типизированному каталогу.
```

Порядок: грант владельца на Q3_AMDL_V0_SHADOW_BACKTEST → V0 → T1..T4 как V1.

## Что судья убил в этом дизайне — читать до всего остального

| Моё решение | Вердикт | Чем заменяется |
|---|---|---|
| kernel-зелёный = узел закрыт | **убито** | три статуса: `SOURCE_WRITTEN` → `KERNEL_GREEN` → `SEMANTICALLY_ADMITTED`; потреблять можно только третий |
| `codex exec resume --last` | **убито** | закреплённый `SESSION_ID`; `--last` берёт свежайшую сессию в cwd, а не владельца задачи |
| `pgrep -f "codex --yolo"` как проверка | **убито** | `flock`/atomic mkdir на весь рантайм; pgrep ловит одно написание и имеет гонку между проверкой и запуском |
| три состояния `OPEN/ANSWERED/DROPPED` | **убито** | четыре: `OPEN → IN_REVIEW → ANSWERED`, ветка `DROPPED` только до claim |
| корреляция одним идентификатором | **усилено** | плюс `REQUEST_BLOB` и `SOURCE_COMMIT`: один ID допускает тихую подмену текста под тем же именем (C09) |
| `STATUS` правится внутри `CODEX_REQ` | **убито** | тело запроса неизменяемо (append-only контракт); состояние живёт в отдельном `CODEX_REQ_STATE_<id>.yaml` через compare-and-swap |
| бессрочный глобальный `CODEX_GRANT` | **убито** | `CODEX_AUTONOMY_LEASE_V1` — привязан к версии контроля, ветке, worktree, замку, фазе, задаче и явному сроку |
| непустой `TRIED` как допуск запроса | **недостаточно** | `phase_key` + `blocker_fingerprint` + шесть no-delta циклов, из существующего бюджета контроля |

Прецедент, на котором стоит весь ремонт, — наш собственный: гейт был зелёным,
квитанции верными, а несущая посылка ложной для нужного объекта. Три имени не
дают трёх независимых ключей. Если второе тело только сверяет квитанции первого,
контур остаётся одним телом с курьером.

**Карантин:** ровно один kernel-зелёный push может ждать семантической приёмки.
Пока он не принят — следующий узел не стартует, `spine` статус не повышает,
и никто не строит теорему поверх этого коммита. Иначе автономный контур
за ночь построит пять корректных теорем на одной ложной посылке.

## Зачем

Трое суток Linux-тело работало одно и накопило пять семантических расхождений,
которые ядро пропустило, потому что все они были в связках и формулировках, а
не в доказательствах. Аудит Codex нашёл их за один заход. Вывод: второе тело
окупается, но только если его не надо каждый раз заводить руками.

## Разделение ролей

```
CODEX    пишет Lean, решает сам, гейтует своим ядром, коммитит, пушит.
         Упёрся в стену → пишет CODEX_REQ_*.md и пушит. НЕ ходит к судье сам.

LINUX    оркестратор. Ловит пуши вахтой, читает запросы, формулирует вопрос
         судье, несёт вердикт обратно, пишет задание, двигает фронт.
         ЕДИНСТВЕННЫЙ с браузером — это его незаменимая часть.

ПРОШКА   судит, убивает, разлагает стены на этажи. Отвечает вердиктом в репо.

ВЛАДЕЛЕЦ границы, ратификации, PX_RH_CLAIM, указатель CURRENT.md.
```

## Такт контура

```
1. CODEX работает, коммитит, пушит                          [CODEX_GRANT]
2. упёрся → docs/routeB_bus/CODEX_REQ_<дата>_<тема>.md, пуш [CODEX_GRANT]
3. вахта Linux видит пуш → будит тело                       [механика]
4. Linux читает запрос, формулирует, пингует судью браузером [NIGHT_GRANT]
5. судья пушит вердикт
6. вахта будит Linux снова
7. Linux пишет docs/Codex/TASK_*.md, пушит                  [NIGHT_GRANT]
8. Linux триггерит Codex                                    ← см. ниже
9. → пункт 1
```

## Триггер — решённый вопрос

```bash
codex exec resume --last "<короткая строка>"      контекст ЦЕЛ, не новая сессия
codex exec resume --last "..." -o /tmp/reply.md   его ответ ложится ФАЙЛОМ
codex exec ... --json                             события построчно
codex exec ... --output-schema FILE               структурированный ответ
```

`-o` важнее, чем кажется: **читать ответ Codex браузер не нужен**, в отличие от
судьи. Значит звено 8→1 полностью механическое.

ОГРАНИЧЕНИЕ, проверено 21.08: если у Codex ЖИВА интерактивная сессия
(`codex --yolo` в терминале), `exec resume` создаёт конкурирующую. Триггерить
можно только когда интерактивной нет. Проверка одной строкой:

```bash
pgrep -f "codex --yolo" >/dev/null && echo "ИНТЕРАКТИВНАЯ ЖИВА — не триггерить"
```

## Дисциплина Codex — формулировка владельца, записать в шапку каждого задания

> **Сокращай пространство решений, а не расширяй.** Нашёл два пути — убей один
> измерением, а не оставляй оба. Проверяй варианты сам: у тебя есть ядро,

Это ровно то правило, которого не хватало: без него второе тело начнёт плодить

## Обратный путь: как Codex узнаёт, что это ответ на ЕГО вопрос

Связывает всё **один идентификатор**, живущий от вопроса до ответа.

```
Codex пишет     docs/routeB_bus/CODEX_REQ_2026-08-21_w13-7b-wall.md
                внутри:  CODEX_REQ: 2026-08-21-w13-7b-wall
                         STATUS: OPEN
                         ↓ коммит + пуш                      [CODEX_GRANT C3]

вахта Linux     видит CODEX_REQ в diff → будит тело

Linux           читает, формулирует, несёт судье браузером
                судья пушит вердикт

Linux пишет     docs/Codex/CODEX_ANSWER_2026-08-21_w13-7b-wall.md
                внутри:  ANSWERS_REQ: 2026-08-21-w13-7b-wall   ← ТОТ ЖЕ ID
                         VERDICT_PATH: docs/routeB_bus/proshka/PROSHKA_VERDICT_...md
                         VERDICT_BLOB: <blob>
                         DECISION: <что решено, одной фразой>
                         NEXT_NODE: <что делать дальше>
                         FORBIDDEN: <что судья запретил>
                и переключает в самом CODEX_REQ:  STATUS: ANSWERED → <путь ответа>

Linux триггерит codex exec resume --last \
                  "Ответ на твой CODEX_REQ 2026-08-21-w13-7b-wall лежит в
                   docs/Codex/CODEX_ANSWER_2026-08-21_w13-7b-wall.md.
                   Сделай pull и продолжай."
```

**Почему именно так, а не через `CURRENT.md`.** Указатель `CURRENT.md`
владельческий и переключается редко — он выбирает КРУПНУЮ задачу. Ответ на
частный вопрос внутри задачи — не смена задачи, и гонять через владельческий
указатель каждую реплику значит превратить его в чат. Ответ едет отдельным
файлом, а `CURRENT.md` остаётся тем, чем задуман.

**Почему ID, а не «последний вердикт».** Тел трое, вердикты идут потоком, и
«последний» через час уже не тот. Идентификатор переживает и паузу, и
перезапуск любого тела: Codex, проснувшись через сутки, по своему же
`CODEX_REQ` найдёт `STATUS: ANSWERED` и путь.

**Три состояния, и все видны грепом:**

```
STATUS: OPEN       вопрос задан, судья ещё не ответил
STATUS: ANSWERED   ответ лежит там-то
STATUS: DROPPED    вопрос снят самим Codex (нашёл решение сам)
```

Последнее важно: если он разобрался сам, пока ждал, он обязан снять свой
запрос, а не оставлять судью работать вхолостую.

## Формат CODEX_REQ

Чтобы вахта Linux отличала стену от обычного пуша, файл обязан начинаться с:

```yaml
CODEX_REQ: <дата>-<короткий-slug>
WALL: <что именно не проходит, одной фразой>
TRIED: <что уже попробовано и почему не сработало — НЕ пусто>
NEED: <какое решение судьи разблокирует>
BLOCKS: <какой этаж стоит>
```

`TRIED` пустым быть не может. Это и есть проверка «стена, а не размышление».

## Чего в контуре НЕТ и не будет

Автоматического повышения Route B. Автоматического заявления RH. Автоматической
правки глобальных правил. Триггера судьи мимо Linux-тела. Всё это остаётся за
владельцем, и контур существует, чтобы приносить ему решения, а не принимать их.

# Очередь к Прошке — накопительная

**Дисциплина очереди (2026-08-20):** каждый запрос несёт `REQ-<дата>-<буква>` и
`STATUS: OPEN | ANSWERED → <файл вердикта>`. Статусы переключает Linux-тело
после жатвы вердикта; судья статусы не трогает, но обязан в вердикте называть
`REQ`-id, на который отвечает. Судья читает этот файл при старте каждой
нетривиальной сессии (его протокол, STANDING REPO FETCHES) и отвечает на
OPEN-запросы от старшего к младшему.


**Пересобрана 2026-08-10** после выходных на Маке. Что изменилось — в разделе
«Состояние фронта» сразу под правилами.

**Как это работает.** Мы с владельцем заходим в фазу и молотим её сами. Всё, что упирается
в тупик или не проверяется отсюда, **не отправляется поштучно**, а копится здесь. Когда
набирается **2–4 вопроса**, без которых дальше только теряем время, — уходит одним батчем.

**Почему кумулятивно.** Прошка думает над батчем 20+ минут и отвечает разбором, а не
репликой. Поштучные вопросы тратят этот ресурс на мелочи и дробят её контекст. Один батч из
четырёх связанных вопросов даёт вердикт, который двигает фронт; четыре батча по одному дают
четыре ответа, которые надо потом сшивать самим.

**Что сюда НЕ попадает** — то, что мы обязаны проверить сами и это дёшево:

| Вопрос | Чем закрывается у нас |
|---|---|
| «есть ли у нас X?» | `./ask.sh X` — шесть хранилищ разом |
| «что уже убито про Y?» | `kb.py ask` · `kb.py flags` |
| «есть ли статья Z?» | `ask.sh` → если нет, `WebSearch` + `./paper.sh` |
| «что доказано в Lean?» | `ask.sh` · живое дерево |
| «врёт ли инструмент?» | запустить и посмотреть |
| «что дешевле закрыть следующим?» | `python3 docs/cartographer/cheap.py` |
| численный зонд | посчитать |

Отправить Прошке то, что решается командой `ask.sh`, — это потратить 20 минут её работы на
то, что стоило две секунды нашей.

**Что сюда попадает:**

1. **Судейское решение** — какой из путей канонический, что убить, что ратифицировать.
2. **Чтение первоисточника, которого у нас нет.** Она читает статьи и проверяет наши
   пересказы; мы читаем диск. Смешивать уровни доверия нельзя.
3. **Архитектурная развилка**, где ошибка стоит смены работы и дороже, чем ожидание.
4. **Kill-pass на нашу собственную конструкцию** — когда нужен тот, кто заинтересован её
   сломать, а не подтвердить.

**Правило по непроверенному.** Утверждение о первоисточнике сперва **проверяется**:
литразведка, база, `ask.sh`, поиск. Если не верифицируется отсюда — записывается в артефакт
как `relay, не верифицировано`, **никогда не используется как посылка вывода**, и ложится
сюда как кандидат в следующий батч.

**Формат записи:**

```
## Q<n> · <короткое имя> · <статус: OPEN | В БАТЧЕ <дата> | ЗАКРЫТ <дата>>
**Блокирует:** что именно встало · **Стоимость ошибки:** во что обойдётся угадать неверно
**Что меняется в действиях:** при исходе A → <ход>; при исходе B → <ход>
### Вопрос
### Что мы уже проверили сами
### Почему отсюда не решается
```

# Что изменил вердикт GLOWER (разбор 2026-08-10)

**Он атакует ровно ту стену, которую генеалогия называет главной.** В `GENEALOGY.md` §8
записано `a = 4.71997997950943e-59` и провал равномерности: `β*_120 = 3.0559e-55` →
`β*_240 = 2.4779e-55`, падение 18.9%, `inf_N (β*_N − a) > 0` НЕ ДОКАЗАНО, узкое место —
odd-сектор. Вердикт требует `c₀ = 1e-58 > 4.719980e-59` — то же самое число.

**Смена стратегии.** Вместо ещё одного расчёта `β_N` доказывается бесконечномерная
теорема `Q₁₃^odd(f) ≥ c₀‖f‖²`. Тогда для каждого `N` компрессия даёт `β*_N ≥ c₀`
автоматически, а `L = inf_N β*_N ≥ c₀ > 0`. Механизм — Feshbach/Schur: голова `H_R`
плюс хвост `T_R`, хвост закрывается коэрцитивностью высоких мод (`D_c ⪰ dI`), голова —
одним конечным сертификатом `B_c − d⁻¹R_c*R_c ⪰ 0`.

**Что вердикт объявил убитым:** дальнейшая экстраполяция `β_N`; `N = 480` как шаг
доказательства; оценки через абсолютные суммы строк; `W02` как положительная часть;
поточечная положительность полного символа. Плюс явные запреты в
`SELECTED_REPRESENTATION`: `absolute_row_sums`, `N_extrapolation`, `Aitken`,
`pointwise_multiplier_positivity`, `finite_PSD_as_global_proof`.

**Три названных пробела:** `OddSourceWeilCompression13` (цена низкая) ·
`YoshidaTailCoercivity13Explicit` (средняя, объявлен минимальным named gap) ·
`OddResidualFeshbachLower13` (низкая абстрактно, средняя на инстанцирование).

**Директива исполнителю:** `READ_ONLY_MATH_AND_NUMERICAL_PREFLIGHT`, `NO_REPO_WRITE`,
`NO_LEAN_EDIT`, задачи `TASK_A` / `TASK_B` / `TASK_C`.

**Что осталось, в явном виде.** Пусть `L = L_m = log m`, окно `[-L/2, L/2]`,

```
density = L^(-1/2) · Σ_{n=-N}^{N} (-1)^n c_n e(nt/L)
denom   = sqrt(L) · |c_0|
```

тогда утечка не зависит от масштаба ряда — оба множителя несут по одному `c`:

```
leakage = (1/L) ∫_{-L/2}^{L/2} |P(t)| · e^(σ|t|) dt,   где P — ряд,
          нормированный на c_0, то есть с нулевым коэффициентом ровно 1
```

Цель: `leakage ≤ C_σ` равномерно по k, при `0 ≤ σ < 1/2`.

**Где напряжение, и почему грубая оценка не проходит.** Невзвешенное среднее
`|P|` по окну не меньше `|P̂(0)| = 1`. Вес `e^(σ|t|)` растёт от 1 в центре до
`e^(σL/2) = m^(σ/2)` на краю. Значит требование равносильно тому, что **`P`
обязан быть мал именно там, где вес велик** — на краю окна, с темпом,
компенсирующим `m^(σ/2)`.

А нормировка стоит **в центре**. То есть условие нормировки и условие убывания
живут на противоположных концах окна. Это и есть та самая endpoint leakage,
которую журнал 27.07 назвал причиной статуса `REPAIRABLE_LEAK`.

## Вопрос (2026-08-25, Linux): где именно живёт кофинальная скорость W5

Разбор перед вопросом, чтобы батч не стоил тебе разведки.

**Декомпозиция бюджета.** Публичный `selectedFerrersAbelLogJumpBudget` после
ремонта устроен так:

```
J(k) = ‖g_k(0)‖ + ‖g_k(L_k)‖ + Σ_{n=2}^{k+2} ‖ √(λ_k/n) · h_k(λ_k) ‖
```

Существенное: аргумент пакета в сумме **не зависит от `n`**. Он всегда `λ_k`.
По `n` меняется только скалярный множитель. Значит сумма выносится:

```
Σ_{n=2}^{k+2} √(λ_k/n) · ‖h_k(λ_k)‖ = ‖h_k(λ_k)‖ · √λ_k · Σ_{n=2}^{k+2} n^{-1/2}
```

**Множитель посчитан численно** (зонд, не в репо; `λ_k = √(k+2)`):

| k | Σ n^{-1/2} | √λ_k · Σ | 2(k+2)^{3/4} |
|---|---|---|---|
| 10 | 4.611 | 8.582 | 12.895 |
| 100 | 17.788 | 56.530 | 64.192 |
| 1000 | 60.864 | 342.436 | 356.189 |

То есть третий член ведёт себя как `2(k+2)^{3/4} · ‖h_k(λ_k)‖`, асимптотика
сходится сверху.

**Отсюда весь вопрос кофинальной скорости сводится к одной величине** —
значению производственного пакета точно на краю окна. Для ограниченного `C_k`
нужно `‖h_k(λ_k)‖ = O(k^{-3/4})`.

**Чего на полке нет.** `./ask.sh` по моде даёт только `normalizedPhysicalMode_normalized`
(`L²`-нормировка) и носитель. Поточечной оценки на краю нет ни одной. Из одной
`L²`-нормировки её не вывести: равномерное распределение массы по окну длины
`2λ_k` дало бы лишь `‖h‖ ~ k^{-1/4}`, и тогда третий член растёт как `k^{1/2}`.

**Маршрут, который видно отсюда.** У нас уже доказана липшицевость пакета на
окне (`selectedPacket_lipschitz_on_window`). Липшицевость плюс `L²`-нормировка
дают поточечную оценку интерполяцией: если `|f(x₀)| = M` и `f` липшицева с
константой `Lip`, то `|f| ≥ M/2` на отрезке длины `M/Lip` вокруг `x₀`, откуда


## Разбор (2026-08-25, Linux): почему L1-компонента может не расти

Не вопрос — заготовка перед следующим узлом, чтобы ты видел маршрут до того,
как я начну его формализовать.

**Что оценивается.**

```
L1_k = ∫_0^{L_k} ‖rep_k(x)‖ dx,
rep_k(x) = √(e^x/λ_k) · Σ_{n=1}^{k+2} h_k(n·e^x/λ_k)
           + (1/2)·h_k(0)·√(e^x/λ_k)
```

**Наблюдение.** F72.6 даёт равномерную по окну оценку

```
‖h_k(y) − 4·H(y)‖ ≤ C/λ_k²   для всех |y| ≤ λ_k
```

Суммируем её по всем активным индексам. Индексов ровно `k+2`, и

```
(k + 2) · C / λ_k²  =  (k + 2) · C / (k + 2)  =  C
```

потому что `λ_k² = k + 2` точно, а не асимптотически. То есть **накопленная
ошибка приближения не растёт по k вовсе** — она ограничена той же константой
`C`, что и одиночная оценка. Число слагаемых растёт ровно так же, как убывает
каждое.

Остаётся главный член `4·Σ_n |H(n·u)|`, где `H` — явная полиномиально-
гауссова цель. Сумма по `n` от гауссианы при фиксированном `u > 0` мажорируется
геометрически, и в отличие от коэффициентов Ферререса здесь всё выписано
явно — тот же материал, что уже дал `explicitCCMLimitH_inverse_four_decay`.

**Что это значит.** L1-компонента выглядит принципиально легче шва: там
пришлось бить край, здесь работает равномерная оценка плюс точное сокращение
`(k+2)/λ² = 1`. Оснований ждать роста я пока не вижу, но и оценки ещё нет —
пишу это как маршрут, не как результат.

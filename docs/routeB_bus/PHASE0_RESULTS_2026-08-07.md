### Вывод соответствия параметров (без подгонки)

Приравниваем окна: их `[λ⁻¹, λ]` против нашего `I_m = Icc (√m)⁻¹ (√m)` ⟹ **`λ = √m`**.
Отсюда `L = 2 log λ = 2 log √m = log m = L_m` — **следствие подстановки**, а не выбор
константы. Мера `du/u` = наш `dStar = volume.withDensity u⁻¹`. Мода
`(1/√L)·e^{2πin·ln(λu)/L}` = наш `V_n_m i n` дословно.

Если бы `L` подбиралось под совпадение, плант `P_R6_1_INDEX_LENGTH` был бы прав; здесь
подбирать нечего.

### Полюсный блок — сильнейшая из проверок

Две формы, выведенные разными путями (Groskin Lemma 2.1):

```
A:  разделённая разность от  ψ₀(x) = C_c·x/(x²+β²),  C_c = L(√c + 1/√c − 2)/(2π²), β = L/4π
```

сверил с пакетом».

## R2 · Архимедов блок брутфорсом по `T` — НЕ СОШЁЛСЯ, Phase 1 заблокирована

Элементы `K`, посчитанные при растущем катоффе архимедова интеграла:

```
T=  20   K[0,0]=0.018317   K[2,3]=0.025741
T=  40   K[0,0]=0.027543   K[2,3]=0.036644
T=  80   K[0,0]=0.034369   K[2,3]=0.043754
T= 160   K[0,0]=0.038749   K[2,3]=0.048178
```

Приращения `0.0092 → 0.0068 → 0.0044`, отношение около `0.7` — сходимости нет, ошибка при
`T = 160` порядка **20–30 %**.

**Это ровно предсказано Groskin:** бюджет `B_T ~ (2N+1)ρ·log T/(π²T)` убывает как `log T/T`,
то есть каждое удвоение `T` покупает около одного двоичного разряда. Его вывод дословно:
*«deep spectral scales are unreachable by brute cutoff; the correct finite instrument at
depth is the cutoff-free assembly itself»*.

**Причина, установленная разбором:** при больших `r` подынтегральное ведёт себя как
`h₊(r)·S(r,x,L) ~ log(r/2π)·sin(2πx)·sin(rL)/r` — **условно сходящийся осциллирующий
интеграл**. Обычная квадратура на конечном отрезке такой хвост не берёт.

**Следствие для сертификата.** Блоки по отдельности порядка единиц (`prime −2.94`,
`pole +5.87`, `arch −2.90`), а их сумма `0.0275` — **сокращение на два порядка уже на
диагонали при `m = 13`**. Ошибка в 20 % в архимедовом блоке полностью съедает результат.
Отсюда же понятно, почему `ε_N` уходит в `10⁻⁵⁵` при больших матрицах: сокращение
накапливается.

**Действие по директиве:** `on_failure: run_numerics: false`. Phase 1 не запускается, пока
архимедов блок не считается надёжно. Структурная часть Phase 0 при этом зелёная — блокирует
именно численный метод, а не кросс-волк.

## R3 · Устранимая особенность найдена и снята; хвост остаётся нерешённым

### R3a — точная замкнутая форма ядра

Подстановка `BL = A` (где `A = 2πx`, `B = 2πx/L`) в мои же промежуточные выражения даёт

```
S(r,x,L) = B·(cos A − cos rL) / (r² − B²)          — ТОЧНО, не асимптотика
```

Совпало с прямой квадратурой до `10⁻³¹` на четырёх точках из пяти; пятая (`4·10⁻¹⁹`) — это
точность самой квадратуры при `dps = 30`, а не расхождение формул. Мой первоначальный порог
`10⁻²⁰` для сравнения аналитики с **численным** интегралом был выбран неверно.

**Следствие:** подынтегральное ведёт себя как `log r / r²` — интеграл сходится
**абсолютно**, а не условно, как я утверждал в R2. Ту оценку снимаю.

### R3b — корень всех неточностей: устранимая особенность `0/0`

При `r = B` имеем `BL = A`, поэтому **числитель тоже обнуляется**: `cos A − cos(BL) = 0`.
Особенность устранимая, но численно это `0/0` — катастрофическая потеря значащих цифр в
окрестности `r = B`. Она сидела во **всех** предыдущих прогонах, включая брутфорс по `T`
из R2.

Снята переписыванием через синусы, где деления на `(r−B)` нет:

```
(cos A − cos rL)/(r − B) = L · sin((A + rL)/2) · sinc(L(r − B)/2)
```

Проверено **в самой особой точке**: обе формы дают ноль; при `r = B + 10⁻¹²` совпадают до
`3·10⁻¹⁹`.

### R3c — что осталось нерешённым

`ψ_arch` по-прежнему не сходится: разброс по точке сшивки `≈ 10⁻³`, и он **растёт линейно
по `x`** (`0.00096 / 0.0019 / 0.0029` при `x = 1,2,3`). Это подпись хвоста — главный член
`B·cos(A)·(log R + 1)/R` линеен по `B = 2πx/L`. Проблема не в ядре, а в том, что
`mp.quad(…, [R, ∞])` не берёт осциллирующий хвост, а `mp.quadosc` на нём не укладывается в
время.

**Состояние блоков:**

| блок | реконструкция | точность |
|---|---|---|
| prime | прямая сумма по `q = p^a ≤ c` | точная |
| pole | **две независимые замкнутые формы** | `10⁻³¹` |
| arch | голова численно + хвост | **`10⁻³` — недостаточно** |

При элементах `K` порядка `0.03` и сокращении между блоками на два порядка ошибка `10⁻³`
съедает результат. Phase 1 остаётся заблокированной.

**Вывод по методу:** дальше не изобретать. Groskin прямо пишет, что правильный инструмент —
**cutoff-free сборка**, и его reproducibility-пакет (`10.5281/zenodo.21124802`) её содержит,
вместе с интервальными сертификатами Arb. Следующий шаг — взять готовое, а не строить своё.

## R4 · Сверка с внешним эталоном — prime и pole ПОДТВЕРЖДЕНЫ

Reproducibility-пакет Groskin скачан (`10.5281/zenodo.21146461`, 508 861 Б, 48 файлов).
В нём `threeroute_c13N4_package.json` — эталон **ровно для нашей контрольной ячейки**
`c = 13`, `N = 4`, `dps = 40`, с разложением по блокам и вектором `v`.

### Что сверено

Посчитал вклад prime-блока **по формуле статьи**, на их векторе, своим кодом:

```
ψ_p^{(c)}(x) = −(1/π) Σ_{q=p^a≤c} (Λ(q)/√q)·sin(2πx(1 − log q/L))
(Q_ψ)_{mn} = (ψ(m) − ψ(n))/(m − n),  m≠n;   ψ′(m),  m=n
u₀ = v₀,  u_k = u_{−k} = v_k/√2
⟨v, Q_prime v⟩ = Σ_{m,n} u_m u_n (Q_ψ)_{mn}
```

| | значение |
|---|---|
| моя реконструкция | `0.0022709319187710444757414793544881` |
| их `route2_prime` | `0.00227093191877104439401560378693` |
| относительная разность | **`3.6·10⁻¹⁷`** |

**Совпадение на 17 значащих цифрах.** Их вектор `v` дан в JSON с 20 знаками — значит
`3.6·10⁻¹⁷` есть **предел точности входных данных**, а не расхождение формул. (Мой порог
`10⁻²⁵` для результата, посчитанного по двадцатизначному входу, был выбран неверно —
третий раз за фазу одна и та же ошибка с порогами.)

**Полюсный блок:** мой `3.9·10⁻⁴²` против их `−2.2·10⁻⁴¹` — оба машинный ноль; вектор
полюс-нейтральный, как и помечено в их собственном поле.

### Техника хвоста, найденная в их коде

`verify_dictionary_threeroute.py::ranktwo_tail` — то, до чего я не додумался за три попытки:

```
sin²(Lr/2) = ½ − cos(Lr)/2
```

* **гладкая половина** — квадратура по **геометрической** сетке `[T₀, 2T₀, 8T₀, 64T₀, 1024T₀, ∞]`;
  для подынтегрального `~log r/r²` каждый отрезок вносит сопоставимый вклад. Я гнал
  равномерный `[R, ∞]` одним куском — отсюда провал R3c;
* **косинусная половина** — **два интегрирования по частям**: граничные члены
  `−G(T₀)sin(LT₀)/L`, `−G′(T₀)cos(LT₀)/L²`, остаток с `G″` по сетке из 60 периодов, плюс
  явная мажоранта `(1/L²)∫|G″|`. Осцилляции не берутся квадратурой вообще — они
  дифференцируются в затухающий остаток.

Их `F(r) = (p_r·u)² + (q_r·u)²`, `p_r·u = Σ u_n/(a−n)`, `a = r/ρ` — это и есть
«rank-two Cauchy–Stieltjes» из Theorem 3.2, в явном виде.

## Три ошибки, сделанные внутри фазы

1. **Порог сравнения выбирался неверно трижды** — сравнивал аналитику с численным
   интегралом требуя `10⁻²⁰`, потом результат по двадцатизначному входу требуя `10⁻²⁵`.
   Каждый раз печаталось «FAIL» там, где совпадение было предельным. Урок: порог задаётся
   **точностью худшего из входов**, а не желаемой.
2. **Утверждение «условно сходящийся интеграл» в R2 было неверно** — после вывода точной
   формы ядра видно, что подынтегральное `~log r/r²`, сходимость абсолютная. Снято в R3.
3. **Устранимая особенность `0/0` при `r = B`** сидела во всех прогонах, включая R2, и
   портила точность. Найдена и снята только в R3b.

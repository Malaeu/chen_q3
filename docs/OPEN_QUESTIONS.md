## 1. Подъём измерения — три `NUMERIC` цепочки PSD

**Что это.** Шаги 8, 13, 14 цепочки `PSD_CERTIFICATE_FOR_CCM_CELL` держатся на
числах из одного файла:
`docs/routeB_bus/phase1_results/ccm_control_cell_m13_N120_interval.json`

```
шаг  8   ε — рэлеевская нижняя граница      241 пивот положителен, Arb, 240 dps
шаг 13   a = ⟨q,Kq⟩ = 4.71998e-59           строгий интервал
шаг 14   β = 1e-56,  β − a = 9.95280e-57    запас положителен
```

**Считать заново НЕ надо.** Числа посчитаны и верны — интервальная арифметика Arb
не врёт. Проблема не в точности, а в **форме**: Lean не принимает JSON.

**Что делать руками.** Превратить числа в объект Lean через уже работающую машину:

```
PSD_PenaltyCertificate.lean            аппарат готов, 0 sorry
  ratWeightedSquareMatrix w L          матрица как сумма взвешенных квадратов
  weightedSquareSum_nonneg             веса ≥ 0 ⟹ форма ≥ 0
       ↓
Matrix.posSemidef_iff_dotProduct_mulVec    (Mathlib)
       ↓
PosSemidef как объект Lean
```

Механика: взять LDL-разложение, **округлить до рациональных**, предъявить точное
тождество в ℚ, проверить веса. Если тождество сошлось — приближения не осталось
нигде. Обкатано на Step32F k=11 (`primaryK11PenaltyLowerBoundCert_ldl`).

**Цена.** Перенос работающей машины на другой вход. Два известных шага:
(а) применить к `ccmShiftedWeilMatFinite`, (б) вещественный сертификат →
комплексный `PosSemidef` для эрмитовой матрицы. Не открытая проблема.

**Что закрывает.** Три шага разом — все висят на одном JSON.

## 2. `SIMPLE:1` — конкретная семья против абстрактного слота

`MISMATCH`. Вещественность нулей доказана для **конкретной** CCM-семьи
(`ccmSourceLagrangePolynomial_..._of_bottomRayleigh_simple`,
`CCMFiniteWeilBottomSpectral.lean:61`), а слот `Theorem510RealZeroBridge`
сформулирован для абстрактной `C.Pstar.family`.

Обе стороны существуют — не хватает переходника. Что именно расходится
(только запись или содержательно) **не проверено**.

**Цена.** Часы, если переформулировка. Неизвестно, если расхождение содержательное.

## 4. Три поля в структуры — ветка B целиком

Установлено 09.08: три оставшихся входа ветки B — не теоремы, а **условия на
входные данные**. Конструкторов у `CanonicalData` и `ProlateKTrialSourceData`
в проекте **ноль**, обе всегда параметр. Значит добавление полей не ломает ничего.

```
trialNormBddBelow : ∃ c > 0, ∀ i, c ≤ ‖gTrial_m_N i …‖
                    рядом с trialNonzero, D0ProlateKTrialSource.lean:50

соотношение скоростей: N_k / log(m_k) → ∞
                    рядом с parentCofinal, D0CanonicalApproximation.lean:71

энергии: суммируемость + ограниченность по k
                    рядом с eStar_memLp, D0ProlateKTrialSource.lean:46
```

**Граница честности.** Формализация от этого не доказывает больше — обязательство
переезжает к тому, кто однажды принесёт настоящие данные. Но вопрос становится
конечным и выписанным.

**Цена.** Внутри проекта — ноль правок. Снаружи — настоящая работа.

## 5. Поточечное → равномерное: один приём на две ветки

Обе ветки упираются в одну подмену квантора (см. правило `pointwise-vs-uniform`):

```
ветка A   hpos/hker1 для ячейки (13,2)  ≠  ∀N
ветка B   ∀k, 0 < ‖gTrial(k)‖           ≠  ∃c>0, ∀k, c ≤ ‖gTrial(k)‖
```

Приём из `B3.0N` (равномерная оценка с явной константой) примерен 09.08 —
**не переносится**: там явная формула через digamma, здесь норма проекции
элемента из данных.

**Открыто.** Есть ли вообще приём, работающий на обе ветки. Если найдётся для
одной — примерить ко второй немедленно.

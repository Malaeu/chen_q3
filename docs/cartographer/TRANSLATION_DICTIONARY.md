# Словарь переводов: наш шаг → утверждение на языке, общем с Mathlib

**Зачем.** Пока незакрытый шаг назван на нашем языке — «`H2aAt` как конкретный предикат»,
«пол odd-сектора ячейки `m=13`» — он несравним ни с чем. Поиск по такой строке не находит
ничего, потому что искать нечего: это имя нашей конструкции, а не утверждение.

Переведённый в термины эрмитовых матриц и внутренних произведений, тот же шаг попадает в
общий словарь с Mathlib и с чужими формализациями — и тогда обнаруживается, что бо́льшая
его часть уже доказана.

Проверено на первом же проходе (2026-08-11): шаг `H2aAt`, числившийся как `GAP`, после
перевода распался на три утверждения, два из которых нашлись готовыми — одно в Mathlib
целым файлом, другое в чужом дереве.

**Порядок ярусов из-за этого изменился.** Было: `comparator` → раздача заданий агентам.
Стало: **словарь → comparator → раздача**. Без словаря агентам нечего раздавать, а
`comparator`-у нечего сверять: обе машины работают с формулировками, а формулировок нет.

**Словарь пополняется по мере работы.** Каждый новый незакрытый шаг, доведённый до
перевода, попадает сюда — независимо от того, нашлись по нему кандидаты или нет.
Ненайденное так же ценно: оно и есть настоящая новая теорема.

```
## <адрес шага в assembly> · <короткое имя> · <статус>

**Перевод:** утверждение в терминах Mathlib — то, что можно искать

Статусы: `ПЕРЕВЕДЁН` (есть формулировка) · `КАНДИДАТЫ` (найдено готовое) ·

Правило записи то же, что везде: **кандидат остаётся кандидатом до прогона Lean**.
Совпадение формулировки не означает применимости — у чужой леммы свои гипотезы и свои
типовые классы.

## Правило: перевод берётся из сигнатуры потребителя

**Формулировку цели не сочиняют — её списывают с того места, куда она пойдёт.**
У каждого незакрытого шага есть потребитель: теорема, принимающая его гипотезой. В её
сигнатуре объект уже записан в точном виде — с носителем, нотацией и связанными
переменными. Это и есть перевод. Всё, что записано иначе, — своя формулировка, и её
промах ничего не говорит о наличии поставщика.

Порядок такой:

```
1. найти потребителя шага            (assembly / knowledge.db → file:line)
2. выписать нужную гипотезу ДОСЛОВНО из его сигнатуры
3. #check предполагаемого поставщика → его точный тип
4. и только теперь сверять — глазами, потом компилятором
```

Шаг 3 отдельный и обязательный: implicit-биндеры и инстансы угадывать нельзя, их печатает
`#check`.

**Откуда правило.** Проба 2026-08-11 по `SIMPLE_EVEN:1`. Потребитель —
`ccmSourceLagrangePolynomial_complex_zerosRealOn_of_bottomRayleigh_simple`
(`CCMFiniteWeilBottomSpectral.lean:61`), и `hbottom` записан в нём так:

```lean
(hbottom : ∀ x : CCMModeFinite N → ℝ,
    epsilon * (x ⬝ᵥ x) ≤ x ⬝ᵥ Matrix.mulVec (ccmWeilMatFinite mProject N) x)
```

Матричный носитель, `⬝ᵥ`, `mulVec`, никаких внутренних произведений. Я же записал в первой
редакции этого словаря `∀ x, ⟪A x, x⟫ ≥ λ₀‖x‖²` — форму, которой в сигнатуре нет. Проба
упала на нотации внутреннего произведения при полностью живом механизме поиска.

Второе, что даёт то же чтение: **в одной сигнатуре потребителя носители уже смешаны** —
`hbottom` матричный, а `hsimple` операторный,
`Module.finrank ℝ ((ccmWeilOpFinite mProject N).eigenspace epsilon) = 1`. Переходник
матрица↔оператор нужен, значит, не для Mathlib, а нам самим внутри своей же теоремы.

**Чего правило не отменяет.** Списанная у потребителя формулировка — всё ещё цель, а не
доказательство. Она лишь гарантирует, что ищут существующий объект.

## SIMPLE_EVEN_GROUND_TO_REAL_ZEROS:6 · H2aAt как конкретный предикат · КАНДИДАТЫ

**Наша формулировка.** `assembly`, шаг 6, статус `GAP`, объекты:
`H2aAt, heig, hnormalized, hbottom, hsimple, Module.Basis`. По генеалогии `H2a` — вход `A`
цепочки `A ∧ B ∧ C ⇒ RH`: простота и чётность нижнего состояния формы.

**Перевод.** Распадается на три утверждения. **Исправлено 2026-08-11** — формулировки
списаны с сигнатуры потребителя `CCMFiniteWeilBottomSpectral.lean:61`, а не сочинены:

```
hbottom   ∀ x : CCMModeFinite N → ℝ,
            epsilon * (x ⬝ᵥ x) ≤ x ⬝ᵥ Matrix.mulVec (ccmWeilMatFinite mProject N) x
heig      Matrix.mulVec (ccmWeilMatFinite mProject N) xi = epsilon • xi
hsimple   Module.finrank ℝ ((ccmWeilOpFinite mProject N).eigenspace epsilon) = 1
```

Три — **не независимы**: `epsilon` связан во всех трёх сразу, и `heig` объявляет его
собственным значением. Первая редакция записывала их через `⟪A x, x⟫` и `λ₀‖x‖²` — формы,
которой у потребителя нет; отсюда и промах вчерашней пробы.

**Кандидаты. ИСПРАВЛЕНО 2026-08-11: `hbottom` и `heig` стояли перепутанными.**

Разбор Прошки (`PROSHKA_H2A_LEAN_NATIVE_PROBE_ADJUDICATION_2026-08-11.md`, пункт 4)
и проверка прогоном показали: Mathlib Rayleigh даёт **существование** нижней собственной
пары, то есть закрывает `heig` вместе со значением `iInf` — а вовсе не `hbottom`.
`hbottom` при **заранее заданном** `epsilon` — это сертификат, и Mathlib сертификатов не
производит. Верное разделение:

```
существование нижней собственной пары   → Mathlib Rayleigh
нижняя оценка при выбранном epsilon     → сертификат проекта (penalty / coercivity)
```

Обе роли совпали бы, только если `epsilon := iInf`; что наш `epsilon` — это `iInf`, надо
доказывать отдельно, и такого утверждения у нас нет.

`heig` (существование нижней пары) — **Mathlib, целым файлом**:

```
Mathlib/Analysis/InnerProductSpace/Rayleigh.lean   (275 строк)
  hasEigenvector_of_isMinOn              минимум частного Рэлея на сфере ⇒ собственный вектор
  hasEigenvalue_iInf_of_finiteDimensional   iInf частного = собственное значение
  iInf_rayleigh_eq_iInf_rayleigh_sphere     iInf по пространству = iInf по сфере
```

Из шапки файла дословно: «если частное Рэлея достигает глобального минимума на сфере в
точке `x₀`, то `x₀` — собственный вектор `T`, а `iInf` — соответствующее собственное
значение». То есть связка «нижняя граница Рэлея ↔ нижнее собственное значение» доказана
для самосопряжённых операторов в конечной размерности.

`hsimple` — **чужое дерево, и НЕ прямой поставщик** (исправлено 2026-08-11, пункт 5
вердикта):

```
zeta-23-lean/Zeta23/LinAlg/Inertia.lean:57
  finrank_range_hermPosPart hM : Module.finrank 𝕜 Vp = posIndex hM
zeta-23-lean/Zeta23/LinAlg/Sylvester.lean:82
  finrank_le_posIndex_of_posDefOn
```

Это машинерия положительного индекса; `finrank (eigenspace A μ) = 1` она напрямую **не
выдаёт** — нужна ещё теорема о ранге-дефекте или о зазоре. Плюс чужое дерево не
импортировано в окружение Q3: **ноль вхождений `Zeta23`** в `q3.lean.aristotle/Q3`, так что
никакой поиск его не увидит. Статус: `механизм-кандидат · требуется перенос · не
поставщик`. Apache 2.0 — идея свободно, код с указанием.

**Настоящий держатель нагрузки — свой, и он уже доказан.**
`H2aPenalty.H2a_SimpleEvenGround_FromPenaltyCoercivity`
(`H2aPenaltyCoercivity.lean:395`) выдаёт разом нижнее обобщённое собственное значение,
глобальный минимум, зазор, простоту и J-чётность — из точного penalty-сертификата.
Искать поставщиков надо для **восьми его входов**, а не для `hbottom/heig/hsimple` по
отдельности.

**Чего не хватает — уточнено прогоном.**

1. *Переходник носителя.* Наш `ccmWeilOpFinite : Module.End ℝ (CCMModeFinite N → ℝ)`
   (Pi-тип), а Mathlib Rayleigh живёт на `EuclideanSpace ℝ n`. Мост **проверен
   компиляцией**: из `Aᵀ = A` — один терм `isHermitian_iff_isSymmetric.mp h`; см.
   `probes/PROBE_H2A_RAYLEIGH_TYPED_BRIDGE_2026-08-11.md`.
2. *Подъём ℝ → ℂ.* Оба наших станка (`HermitianDeterminantRealZeros.lean:31`,
   `H2aPenaltyCoercivity.lean:395`) объявлены над **ℂ** с `IsHermitian`, а CCM-матрица —
   над **ℝ** с `Aᵀ = A`. Разрыв закрыт на месте: `real_symm_map_complex_isHermitian`,
   шесть строк, аксиомы стандартные.
3. *Сертификат и инстанцирование семьи.* Остаётся настоящий разрыв: конкретные
   penalty-данные для CCM-семьи. Это **не** инстанцирование — это новая работа.

**Проверено.** `rg` по Mathlib, нашему дереву и `zeta-23-lean`; `#check` точных типов;
компиляция моста, явного терма Rayleigh, подъёма ℝ→ℂ и отрицательного контроля;
`#print axioms` — везде стандартная тройка. 2026-08-11.
**На `ccmWeilMatFinite` не инстанцировано** — модуль на этой машине не был собран.

## Проба яруса 3: Lean как судья — механизм работает, узкое место в другом

Проведена 2026-08-11 по разбору Мифоса. Файлы и логи: `docs/cartographer/probes/`.

**Замысел (его М2).** Не строить свой экстрактор сигнатур, а поставить цель как `example`
и дать `exact?` искать в окружении.

> **УБИТО 2026-08-11.** Дальше в первой редакции стояло: «`comparator` перестаёт быть
> отдельным инструментом, `exact?` и есть прогон компилятора». Вердикт Прошки помечает это
> как `FATAL CONCEPT ERROR`, и он прав. Это три разные роли:
>
> ```
> exact?      типизированный отбор + локальный поиск доказательства
> apply?      типизированный отбор + показ остаточных подцелей
> comparator  точное равенство заявленного утверждения доказанному
>             + политика допустимых аксиом + тождество источника и потребителя
> ```
>
> Закрытая локальная цель не гарантирует, что заявленная теорема маршрута не ослаблена.
> `comparator` этим прогоном **не построен и не заменён**.

**Что вышло.**

```
Probe2.lean, третий example        Try this: exact rfl        8 секунд
Probe2.lean, первый и второй       exact? не закрыл цель
Probe.lean,  все три               exact? не закрыл цель      1 мин 47 с
```

**Механизм работает и быстр.** Опасение «утонет на полном Mathlib» снято точечными
импортами: восемь секунд на файл. Найденное `exact rfl` — не кандидат, а принятое
компилятором доказательство.

**Узкое место — формулировка, не производительность.** Чтобы `exact?` нашёл лемму, цель
надо записать ровно в тех терминах, в которых она существует: та же нотация, те же
instance-аргументы, тот же носитель. Записанное наугад даёт промах при полностью живом
механизме. Первый `example` пробы брал **точную сигнатуру существующей** леммы
`hasEigenvalue_iInf_of_finiteDimensional` — и упал на синтаксисе нотации внутреннего
произведения.

**Следствие для архитектуры.** Агент-переводчик нужен не для поиска — поиск бесплатен и
мгновенен. Он нужен, чтобы **записать цель так, чтобы её приняли**. Ярус 3 — это написать
`example`, а не подбор ключевых слов.

**Два факта о нашем пине Mathlib** (`v4.26.0`), пойманные пробой:

- `Matrix.Spectrum` лежит в `Mathlib/Analysis/Matrix/Spectrum.lean`, **не** в
  `LinearAlgebra/`; импорт по привычному пути падает с «object file does not exist»;
- `Mathlib.Analysis.Matrix` объявлен deprecated в пользу `Mathlib.Analysis.Matrix.Normed`.

**Скоринг предсказаний Мифоса** (зарегистрированы до прогона):

| | прогноз | p | исход |
|---|---|---|---|
| `P1` | `exact?` вернёт лемму ≤5 мин на прогретом кэше | 0.55 | время подтверждено (8 с), имя — нет, из-за формулировки |
| `P2` | `hsimple` одношагово из Mathlib не закроется | 0.60 | **подтверждена** |

`P4` (метадамп через environment) и `P5` (doc-gen4 на наших модулях) не проверялись:
после пробы они отодвинуты — пока цели формулируются неточно, дамп сигнатур искать не

**Чего проба не сделала.** Не проверен `apply?` с разбором подцелей — Мифос указывал на

iff-леммы, и найти их — та же задача формулировки.

## Theorem510RealZeroBridge · вещественность нулей выбранного семейства · КАНДИДАТЫ

Прогон №2 конструктора, 2026-08-11. Первый узел, взятый **по правилу** с самого начала:
формулировка списана с потребителя, ничего не сочинено.

**Наша формулировка.** `CanonicalRHRouteSkeleton.lean:114` — `def`, не теорема. Входит
гипотезой `h510` в трёх местах (:136 `selectedFamily_realZeros`, :153 и :185
`rh_of_canonical_strip_slots`). **Поставщиков ноль.**

**Перевод — развёртка определения, дословно:**

```lean
∀ i, H2aAt i → Differentiable ℂ (C.Pstar.family i) →
  ZerosRealOn Set.univ (C.Pstar.family i)
```

где `ZerosRealOn S f := ∀ z ∈ S, f z = 0 → z.im = 0` (`ZeroEscapeLogic.lean:13`).

**Кандидаты — оба свои, оба доказанные.**

```
PosDefSelfAdjointRealSpectrum.lean:18   posDefSelfAdjoint_exists_hermitian
  (Q D : Matrix n n ℂ) (hQ : Q.PosDef) (hSA : Q * D = Dᴴ * Q)
  ⟹ ∃ H, H.IsHermitian ∧ H.charpoly = D.charpoly

HermitianDeterminantRealZeros.lean:31   zerosRealOn_of_hermitian_charpoly_mul
  (M : Matrix n n ℂ) (hM : M.IsHermitian) (F unit realFactor : ℂ → ℂ)
  (hunit : ∀ z, unit z ≠ 0) (hrealFactor : ZerosRealOn Set.univ realFactor)
  (hfactor : ∀ z, F z = unit z * (M.charpoly.eval z * realFactor z))
  ⟹ ZerosRealOn Set.univ F
```

Заключение второго — **дословно** то, что требует потребитель. Заключение первого даёт
ровно два первых входа второго, и сохраняет `charpoly`, поэтому разложение можно писать
через `D`, не через `H`.

**Чего не хватает — ровно одного входа:** `hfactor`, разложение
`C.Pstar.family i z = unit z · (D.charpoly.eval z · realFactor z)` при взвешенно
самосопряжённой `D`. Это и есть «определительное тождество» из докстринга самого
определения — и это **тот же самый разрыв, что `SIMPLE_EVEN:15`**, увиденный с другого
конца: нормировка `c_N`, которой в проекте нет, и связь
`sourceLagrangePolynomial ↔ centeredXi`, по которой ноль теорем.

**Честная оговорка про класс прогресса.** Собранная лемма гипотезу `H2aAt i` **не
использует** — вся нагрузка уходит в `hfactor`. Значит это не снятие посылки у живого
потребителя, а **перенос разрыва** в меньший именованный вход. По шкале вердикта — прогресс
представления, не прогресс доказательства; анти-декорационная защита Прошки здесь бьёт по
нам, и правильно.

**Сборка СКОМПИЛИРОВАНА**, аксиомы `[propext, Classical.choice, Quot.sound]`:

```lean
theorem theorem510_of_weighted_selfadjoint_factorization
    {Index : Type*} (C : CanonicalApproximation Index) (H2aAt : Index → Prop)
    (n : Index → Type) [∀ i, Fintype (n i)] [∀ i, DecidableEq (n i)]
    (Q D : ∀ i, Matrix (n i) (n i) ℂ)
    (hQ : ∀ i, (Q i).PosDef)
    (hSA : ∀ i, Q i * D i = (D i)ᴴ * Q i)
    (unit realFactor : Index → ℂ → ℂ)
    (hunit : ∀ i z, unit i z ≠ 0)
    (hreal : ∀ i, ZerosRealOn Set.univ (realFactor i))
    (hfactor : ∀ i z,
      C.Pstar.family i z = unit i z * ((D i).charpoly.eval z * realFactor i z)) :
    Theorem510RealZeroBridge C H2aAt
```

Доказательство — четыре строки: `posDefSelfAdjoint_exists_hermitian` даёт `H` и
`H.charpoly = D.charpoly`, дальше `zerosRealOn_of_hermitian_charpoly_mul` с переписанным
через `hchar` разложением.

**Грабли прогона.** `(Q i).PosDef` над ℂ не элаборируется без `open scoped ComplexOrder
MatrixOrder`; без них — `failed to synthesize PartialOrder ℂ`. Это не свойство математики,
а область видимости: в файле-источнике строка `open scoped` стоит на :8. Ещё один довод за
правило — тип берут у потребителя вместе с его обстановкой.

**Проверено.** Сигнатуры с диска; сборка модулей `HermitianDeterminantRealZeros`,
`PosDefSelfAdjointRealSpectrum`, `CanonicalRHRouteSkeleton` (7750 задач); компиляция
сборки; `#print axioms`. 2026-08-11.

## hfactor · разложение семейства через определитель · РАЗРЫВ ПОДТВЕРЖДЁН

Прогон №3, 2026-08-11. Вход — единственный оставшийся вход прогона №2.

**Наша формулировка.**

```lean
hfactor : ∀ i z, C.Pstar.family i z = unit i z * ((D i).charpoly.eval z * realFactor i z)
```

**Что стоит за каждым куском — прочитано с диска.**

`C.Pstar` **инстанцирована**, вопреки ожиданию: `D0CanonicalApproximation.lean:83`,
`Pstar := ⟨centeredPstarFamily D.kTrial⟩`. А `centeredPstarFamily` — это

```lean
(centeredXi 0 / rawFplus D i.1 0) * rawFplus D i.1 z
rawFplus D i z := proposition59RawTransform (logLength i) (modeSet i) (D.kTrial i) (-z)
```

то есть **интегральное преобразование**, аналитический объект.

Правая же часть — `charpoly` конечной матрицы, объект алгебраический.

**Разложение у нас есть — но не для того семейства.**

**Мера разрыва.** `centeredPstarFamily` встречается в дереве 20 раз, в пяти файлах

**Вывод прогона: `hfactor` — не сантехника.** Это утверждение «аналитическое интегральное

алгебраическую. Это и есть содержание маршрута, а не недостающая склейка.

Отсюда же уточняется прежняя формулировка `SIMPLE_EVEN:1`. «Доказана для конкретной семьи,
слот просит абстрактную `C.Pstar.family`» звучало как расхождение области. На деле обе
семьи конкретны и **разные по природе**: Лагранж конечно-алгебраичен, `centeredPstarFamily`
аналитична. Расхождение не в общности, а в стороне.

**Проверено.** `rg` по всему дереву; прочитаны `D0CanonicalApproximation.lean:55-90`,

применимости. 2026-08-11.

Типы зависят от индекса (`n ι : Index → Type`) — размерность растёт с `N`, как у CCM;
первая редакция брала один носитель на все индексы и моделировала задачу неверно.

**Скоринг предсказаний Мифоса** (зарегистрированы до прогона, не переписаны после):

| | прогноз | p | исход |
|---|---|---|---|
| `R3-P1` | остаток сожмётся ровно в связку `family ↔ Лагранж` с `c_N`, полка закроет вторую половину | 0.65 | **подтверждено** компиляцией |
| `R3-P2` | `c_N` придётся вводить новым определением, готовой связи нет ни в одном из трёх деревьев | 0.70 | **подтверждено**: ноль файлов, где встречаются оба объекта; ноль в чужом дереве; `c_N` как объявление отсутствует |

**Чего этот разрез НЕ даёт, и это надо держать при себе.**

Одно недостающее **уравнение** — да. Но теорема с полки несёт свои условия на
`T, lam, xi, beta` (`hpos`, `hcomm`, `hTDxi`, `hTxi`, `hker1`), и для CCM-инстанса их
по-прежнему надо поставлять. «Одно звено» — про равенство, не про весь вход.

И прежняя оговорка в силе: `H2aAt` не используется и здесь. Живая посылка у потребителя
не снята — разрыв снова перенесён, теперь в `c_N`.

**Минимальное недостающее тождество всей ветки названо:**
`family i z = c_N i · Лагранж_ℂ(z)` при `c_N i ≠ 0`. Здесь впервые рождается `c_N` как
объект, и это следующий математический гол, а не работа конструктора.

## SIMPLE_EVEN как счёт, а не как локализация · ПЕРЕВЕДЁН, часть доказана

Прогон 2026-08-11, после разбора формализации Anthropic (`zeta-23-lean`). Приём
заимствован как **идея** (Apache 2.0), код не копируется — доказано своим через Mathlib.

**Что у них.** Они подняли безусловную долю нулей на критической прямой с 41.7 % до
2/3, а с оптимальным окном Монтгомери–Тейлора до `2 − 1/c₁* = 0.672501…`
(`ϑ = 1/√2`, `c₁* = √2·tg ϑ/(1 + ϑ·tg ϑ) = 0.753296`; константы пересчитаны нами и
сошлись до последней цифры). Несущая деталь — `Zeta23/LinAlg/RankTrace.lean:163`:

```
P ⪰ 0, rank P ≤ r;  Q эрмитова, n₊(Q) ≤ b;  c > 0
⟹  c·tr P − (c²/4)·r + 2c·tr Q − c²·b ≤ ‖P + Q‖²_F
```

Чистая конечномерная линейная алгебра, ни дзеты, ни нулей. Приём: **сторона нулей явной
формулы превращается в конечный эрмитов блок, и вопрос «сколько нулей вне прямой»
становится вопросом о положительном индексе `n₊`**. Локализация заменена счётом; где
именно нули — так и не выясняется. Применение проверено: `ZeroSide/RankTraceMult.lean`,
`Assembly.lean`.

**Почему это касается нас.** Весь наш `SIMPLE_EVEN` сформулирован как локализация:
где сидит нижнее состояние, чему равно `epsilon`, чему равна кратность. Их язык — счёт.

**Наша формулировка.** `hsimple` потребителя
(`CCMFiniteWeilBottomSpectral.lean:61`):

```lean
Module.finrank ℝ ((ccmWeilOpFinite mProject N).eigenspace epsilon) = 1
```

**Перевод — ДОКАЗАН**, `probes/Probe_Inertia_SimpleAsCount.lean`, аксиомы стандартные:

```lean
theorem ccm_hsimple_iff_rank (mProject N : ℕ) (epsilon : ℝ) :
    Module.finrank ℝ ((ccmWeilOpFinite mProject N).eigenspace epsilon) = 1
      ↔ (ccmShiftedWeilMatFinite mProject N epsilon).rank = 2 * N
```

Работает потому, что `ccmShiftedWeilMatFinite = M − ε•1` дословно (`rfl`), а
`card (CCMModeFinite N) = 2N + 1`. Слева — где сидит состояние. Справа — **число**.

**Вся тройка в языке счёта.** Пусть `S := ccmShiftedWeilMatFinite mProject N ε`:

```
hbottom  ⟺  S ⪰ 0        CCMFiniteWeilBottomSpectral.lean:42
                         ccmShiftedWeilMatFinite_posSemidef_of_bottomRayleigh
heig     ⟺  ξ ∈ ker S, ξ ≠ 0
hsimple  ⟺  rank S = 2N  доказано ниже; при S ⪰ 0 это же есть n₊(S) = 2N
```

Мост `ker ↔ eigenspace` — тоже свой и тоже готовый:
`ccmShiftedWeilOpFinite_ker_eq_eigenspace`, `CCMFiniteWeilBottomSpectral.lean:34`,
восемью строками выше posSemidef-поставщика.

> **Промах, пойманный в тот же день.** Первая редакция пробы доказывала этот мост
> **заново**. Он лежал в том же файле, который я в тот день читал, и в том же файле, где
> живёт потребитель. Проба переписана на существующую теорему. Правило «спроси полку
> первой» нарушено внутри работы, посвящённой тому, чтобы не строить дважды, — записано,
> чтобы не считалось мелочью.

**Счёт режется канонически — центросимметрией, которая уже доказана.**
`ccmWeilMatFinite_centrosymmetric` (`CCMFiniteWeilSourceMatrix.lean:250`) даёт коммутирование
`S` с чётностью, значит `S = S_odd ⊕ S_even`, а `ξ` чётен. Отсюда `2N` распадается на две
именованные подцели:

```
(A-odd)   S_odd ≻ 0                 размерность N, ядра в odd-блоке нет вовсе
(A-even)  S_even ≻ 0 на ξ^⊥         размерность N
```

Прежняя формулировка «вторую половину надо строить, как — не проверено» этим заменяется.

**Соседний станок — обязательная перекрёстная ссылка.** `H2aPenaltyCoercivity.lean`
решает ту же пару «сертификат ⇒ простота», и файла нет в `MAP.md`. Адреса сверены:

```
:102  coercivity          сертификат PosSemidef
:141  J_geig              J-чётность собственного вектора
:157  odd_Gorth           ортогональность odd-сектора
:255  simplicity_clause   простота из сертификата
```

Перед постройкой чего-либо нового в этом направлении — читать его, иначе одна машинка
будет построена дважды (см. промах выше).

> **ЖЁСТКОЕ ПРАВИЛО.** Артефакты GLOWER **не потребляются** поставщиками odd-блока, пока
> не существует явной леммы-моста о конечной компрессии. Язык сомкнулся, объекты — нет:
> бесконечномерный `Q₁₃^odd` и конечная компрессия остаются разными до отдельной теоремы.

**Чем это открывает путь.** Их `Sylvester.lean:82`:

```
finrank_le_posIndex_of_posDefOn : форма положительно определена на W  ⟹  dim W ≤ n₊(A)
```

плюс `posIndex_eq_rank_of_posSemidef` (`n₊ = rank` для PSD). Значит `hsimple`
доказывается **предъявлением подпространства размерности `2N`, на котором сдвинутая форма
строго положительна** — без вычисления собственных значений и без сертификата на зазор.

**И тут смыкаются два наших фронта.** GLOWER требует `Q₁₃^odd(f) ≥ c₀‖f‖²` — это дословно
«форма положительно определена на odd-подпространстве», то есть посылка того же
устройства. В языке счёта коэрцитивность odd-сектора **есть нижняя оценка на `n₊`**.
Два рабочих фронта, которые числились не связанными, — утверждения об одной величине.

**Чего этот перевод НЕ даёт.**

- odd-сектор имеет размерность `N`, а для `hsimple` нужно `2N`: устройство даёт **половину**
  счёта, вторую половину надо строить в чётном секторе. Как — не проверено.
- Их `posIndex`, `hermPosPart`, `finrank_le_posIndex_of_posDefOn` **в нашем дереве
  отсутствуют**: ноль импортов `Zeta23`. Доказанный выше перевод обходится Mathlib, но
  устройство про подпространство — нет, его придётся строить или переносить с указанием
  происхождения.
- Бесконечномерный `Q₁₃^odd` и конечная компрессия — **разные объекты**; смыкание фронтов
  сформулировано на языке, а не доказано.

**Предсказания, зарегистрированы 2026-08-11 до прогона, не переписывать после.**

| | прогноз | p |
|---|---|---|
| `I-P1` | блочная эквивалентность `hsimple ⟺ (S_odd ≻ 0) ∧ (S_even ≻ 0 на ξ^⊥)` компилируется малой кровью из `_centrosymmetric` | 0.70 |
| `I-P2` | устройство «`dim W ≤ n₊`» воспроизводится Mathlib-first, чужой код не понадобится (идея — с атрибуцией в докстринге) | 0.60 |
| `I-P3` | odd-блок **не** выведется из GLOWER без нового моста, родится отдельная лемма | 0.75 |
| `I-P4` | even-половина окажется того же класса, что `simplicity_clause`, и две машинки сольются в одну | 0.50 |

**Δ-зонд не убит, а переклассифицирован.** Инерционный маршрут не нуждается в размере
щели: если зайдёт, вход `A` закрывается **без единой константы**. Зонд остаётся жить как
фальсификатор гауссова сценария для входа `B`. `N = 480` держится как был.

### 1.2. Самый вероятный реальный виновник: ручная периодизация через `HasSum/tsum` + `intervalIntegral` + `EqOn`
То, что ты описал в `integral_P_A_eq_arch_term` (примерно `HasSum (fun n : ℤ => ∫ θ in (-1/2)..(1/2), g (θ+n)) ) ...`) — это ровно тот класс доказательств, где:

- `simp` пытается протащить равенства под `tsum`, под интегралы, под `EqOn`,
- `convert` генерит гигантские задачи на конгруэнцию,
- на каждом шаге подтягиваются “побочные” typeclass’ы (`Measurable`, `Integrable`, `IntervalIntegrable`, `AE*`), и search может разрастись.

Ключевой сигнал: **у mathlib уже есть готовые леммы для этого exact сценария** — и их использование резко уменьшает размер термов и нагрузку.

## 2) Как быстро и точно поймать “медленное место” (без гадания)

### 2.1. Включи Diagnostics Counters
Lean умеет печатать счётчики по подсистемам (`simp`, typeclass synthesis и т.п.):

```lean
set_option diagnostics true
set_option diagnostics.threshold 5
```

Смысл: он будет репортить места, где счётчики превысили порог. Это официально описано в релизах Lean 4.8/4.9. citeturn29search4turn29search2

Практический эффект: если компиляция “зависает”, то последняя напечатанная команда/теорема обычно и есть виновник, а счётчики скажут — `simp` или `typeclass` или `reduction`.

### 2.2. Включи профайлер тактик локально на подозреваемой теореме
Для тактик есть профайлер `trace.profiler`:

```lean
set_option trace.profiler true in
theorem integral_P_A_eq_arch_term ... := by
  ...
```

Это стандартный приём: даёт древовидную раскладку времени по тактикам/подтактикам. citeturn29search3turn29search17

### 2.3. Убери “бесконечность” из heartbeat’ов
Сделай ошибку воспроизводимой:

- Убери `set_option maxHeartbeats 0`.
- Если реально нужна большая квота — ставь **конечную** (например, 2–5 млн) на уровне конкретной теоремы, а не всего файла.

## 3) Рекомендованный rewrite-паттерн (чтобы файл начал компилироваться)

Твой `integral_P_A_eq_arch_term` почти наверняка пытается доказать **классический разбор ℝ на фундаментальный домен длины 1** и сумму по целым сдвигам. Это уже решено в mathlib.

### Вариант A: использовать готовую `Integrable.hasSum_intervalIntegral_comp_add_int` (самый “короткий”)
Идея: вместо ручной сборки `HasSum/tsum` + `Finset.Icc` + “вне диапазона 0”, делай так:

1) докажи `Integrable (fun x => g B t x) volume`;
2) применяй `hfi.hasSum_intervalIntegral_comp_add_int`;
3) если нужно окно `(-1/2)..(1/2)` вместо `0..1`, делай **один** аккуратный сдвиг через `intervalIntegral.integral_comp_add_right` / `..._left`, а не через `convert`‑цепочки. Эти леммы есть в `IntervalIntegral.Basic`. citeturn31view0turn23view0

Скелет (идеологически):

```lean
have hg : Integrable (fun x : ℝ => g B t x) volume := ...
have hsum : HasSum (fun (n : ℤ) => ∫ x in (0:ℝ)..1, g B t (x + n)) (∫ x, g B t x) :=
  hg.hasSum_intervalIntegral_comp_add_int
-- дальше 1 раз переводишь 0..1 -> (-1/2)..(1/2) через integral_comp_add_*
-- и завершаешь `simpa`/`simp_rw`, без `convert`.
```

Факт существования леммы `hasSum_intervalIntegral_comp_add_int` — прямо в docs mathlib. citeturn24search1turn31view0

**Почему это ускоряет:** ты перестаёшь строить огромный ручной терм `HasSum` из кирпичиков, а используешь один “плотный” лемматизированный результат.

---

### Вариант B: фундаментальный домен через `IsAddFundamentalDomain.integral_eq_tsum_of_ac` (самый “концептуально чистый”)
Если тебе принципиально важно окно именно `Ioc (-1/2) (1/2)` или общий `Ioc t (t+1)`, то можно применить machinery фундаментальных доменов:

В `Mathlib.MeasureTheory.Group.FundamentalDomain` есть теорема  
`MeasureTheory.IsAddFundamentalDomain.integral_eq_tsum_of_ac` (и варианты), выражающая интеграл как `tsum` интегралов по translates фундаментального домена. citeturn10view0

Плюс в `IntervalIntegral.Periodic` обсуждается фундаментальный домен `Ioc t (t+T)` для подгруппы `ℤ ∙ T`. citeturn28search1

Это чуть более тяжёлый по зависимостям путь, но он избавляет от ручной “геометрии” покрытия ℝ.

## 4) Что конкретно переписать в твоих “подозрительных местах”

### 4.1. `EqOn` / `Set.uIcc` / `integral_congr` цепочки
Если ты используешь:

```lean
intervalIntegral.integral_congr (h : Set.EqOn f g (Set.uIcc a b))
```

то, во‑первых, это нормально (и такая лемма есть). citeturn31view0turn23view0  
Но в тяжёлых доказательствах лучше перейти на **AE‑версию**:

- `intervalIntegral.integral_congr_ae` / `integral_congr_ae_restrict`, чтобы не заставлять `simp` работать с `uIcc` как с set‑термом, а просто закрывать `AE`‑равенство. Эти леммы тоже есть. citeturn31view0turn23view0

**Паттерн:**
- вместо `EqOn` + `by intro x hx; ...`
- делай `refine intervalIntegral.integral_congr_ae ?_`
- и доказывай `∀ᵐ x ∂(volume.restrict (Set.uIoc a b)), f x = g x` через `Filter.eventually_of_forall` если равенство точечное.

Это обычно уменьшает унификацию и `simp`‑нагрузку.

---

### 4.2. `convert ... using 1 <;> ring` на интегралах
`convert` — полезный, но **дорогой**: он создаёт цели на равенство/конгруэнцию больших выражений и запускает тяжёлую машинерию.

**Заменяй на:**
- `simpa [add_assoc, add_comm, add_left_comm]` если это просто перестановка,
- `simp_rw` с 1–2 леммами,
- или `have` маленьких равенств для концов интервала (типа `by ring`) *до* применения интегральной леммы.

Если ты уже используешь `intervalIntegral.integral_comp_add_right`, то очень часто хватает:

```lean
simpa [add_assoc] using intervalIntegral.integral_comp_add_right (f := ...) (d := (n:ℝ))
```

Вместо `convert`.

Лемма `intervalIntegral.integral_comp_add_right` существует и именно для этого. citeturn31view0turn23view0

---

### 4.3. `Finset.Icc` с `Int.ceil` прямо в границах
Это редко “бесконечно”, но часто **ужасно раздувает** цели, особенно если дальше ты переписываешь/сравниваешь эти границы в `simp`/`linarith`.

**Паттерн стабилизации:**
```lean
let N : ℤ := ⌈B⌉ + 1
let s : Finset ℤ := Finset.Icc (-N) N
```
и дальше никогда не раскрывай `N` обратно в `⌈B⌉ + 1`, пока не надо.  
Если нужно, докажи отдельно леммы вида `abs m ≤ N → ...` и `abs m > N → ...`.

## 5) Best practices именно под твои 3 пункта

### 5.1. `tsum` по `ℤ` при компактной поддержке
- Если поддержка реально конечна: **работай Finset’ом с самого начала** и в конце делай `tsum_eq_sum`/`HasSum` через “finite support”.  
- Если в mathlib уже есть лемма уровня `Integrable → HasSum` (как тут), *не* “опускай” до Finset вообще — это чаще всего быстрее и короче.

### 5.2. `intervalIntegral` и перенос (translation)
- Используй готовые леммы `intervalIntegral.integral_comp_add_right/left` вместо “переписывания границ + convert”. citeturn31view0turn23view0
- Для замены подынтегральной функции: предпочитай `intervalIntegral.integral_congr_ae` (AE‑версия) вместо больших `EqOn` с `uIcc`. citeturn31view0turn23view0

### 5.3. `Finset.Icc` с вычисляемыми границами (`ceil`)
- “Заморозь” границы в локальной константе `N` (см. выше).
- Не давай `simp` трогать `Int.ceil`/`Nat.ceil` без крайней нужды.
- Если нужна арифметика на `Icc`: лучше отдельно держать леммы о включениях/пустоте, чем каждый раз гонять `linarith` по развёрнутым `ceil`.

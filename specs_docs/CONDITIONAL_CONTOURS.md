# CONDITIONAL_CONTOURS — условные контуры: что делали, чем заменены, что превращать в skill

Разбор «дополнительных условных файлов» из порядка чтения. Для каждого: вход, выход, кто
писал, работает ли инструмент **сегодня** (проверено запуском, а не по документу), и на
сколько функция уже перекрыта августовскими изменениями.

Главный вывод вперёд: **почти везде инструмент жив, а документ протух.** Это не одно и то же,
и лечится по-разному — мёртвый инструмент надо оживлять или хоронить, мёртвый документ при
живом инструменте надо просто переписать или заменить на skill.

## 6. Cognitive kernel / operators — самое интересное

| | |
|---|---|

| Governor | `ACTIVE/COGNITIVE_GOVERNOR.md` — 2026-07-31, живее |

Каталог из девяти операторов: `ContinueLocal`, `EscapeLoop`, `RepresentationShift`,
`CertificateShift`, `CounterexampleSearch`, `RouteKill`, `ProshkaReview`,
`MemoryConsolidation`, `ReceiverMinimize`.

**Проверено: ни один из девяти не упомянут в `docs/CODEX_CONTROL.md`.** То есть новый кернел
их НЕ поглотил — вопреки ожиданию, что раздел про `BOUNDED_EXPLORATION_PHASE` их заменил.

**Но словарь жив в данных:** в `knowledge.db` восемь kill-записей ссылаются на
`escape_operator` (`CertificateShift`, `RepresentationShift`, `ReceiverMinimize`,
`MemoryConsolidation`), плюс три записи несут `cognitive_operator = MINIMAL_LEMMA`.

> **Уточнение 2026-08-06** (`SESSION_START_AUDIT_2026-08-06.md` §5.2). Формулировка выше
> занижала диагноз, а по одному пункту вводила в заблуждение:
>
> 1. Те восемь kill-строк — **не независимый потребитель словаря**. Это один и тот же
>    `ACTIVE/FAILED_STRATEGIES.yaml`, затянутый `kb_migrate_kills.py:102`; все восемь
>    с `recorded_at = 2026-07-31` и `source_file = ACTIVE/FAILED_STRATEGIES.yaml`.
>    У девятки **один писатель** — локальный цикл Codex.
> 2. `escape_operator:` в `docs/routeB_bus/` встречается **ноль раз**. Все 20 реальных
>    значений `cognitive_operator_used:` там — из **восьмёрки Прошки** (`MINIMAL_LEMMA` ×14,
>    `UNIT_AUDIT` ×3, `REPRESENTATION_SHIFT` ×1, `LITERATURE_BRIDGE` ×1,
>    `COUNTEREXAMPLE_HUNT` ×1), последние три — сегодняшние вердикты.
> 3. **Точное строковое пересечение двух словарей — ноль.** Четыре пары совпадают по смыслу
>    (`RepresentationShift`↔`REPRESENTATION_SHIFT`, `CounterexampleSearch`↔`COUNTEREXAMPLE_HUNT`,
>    `RouteKill`↔`ABANDON_ROUTE`, `ReceiverMinimize`↔`MINIMAL_LEMMA`), но регистр разный
>    (CamelCase против SCREAMING_SNAKE) — ни grep, ни `kb.py` их не соединит.
> 4. `CODEX_CONTROL.md` не содержит **ни одного** из 17 имён — только состояния
>    `SOFT_STALL`/`HARD_STALL`. Арбитра над диалектами нет.
> 5. База уже копит оба: `MINIMAL_LEMMA` просочился в `journal_entry`,
>    `COUNTEREXAMPLE_HUNT` — в `move`.

**Диагноз: два несовместимых словаря без арбитра.** Мёртвый каталог с одним писателем,
живой фронт пишет непересекающимся набором из файла, который порядок старта читать не велит.
Определения восьми значений `escape_operator` при этом живут **только** в
`COGNITIVE_OPERATORS.md` — выкинуть его значит сделать записи в базе навсегда нерасшифровываемыми.

## 8. Что превращать в skill, а что чинить иначе

**Кандидаты в skills** (повторяемая процедура + понятный вход):

1. **`oracle-query`** — семантический поиск: сформулировать запрос, выбрать коллекцию,
   отранжировать, свести с `kb.py ask`. Инструмент готов, нужен только сценарий.
2. **`aristotle-input`** — подготовка входа: чеклист из `GUIDELINES` (какие тактики избегать,
   структура промпта, обязательные планты, транспортная броня), проверка `kb.py ask` перед
   созданием, оформление в `aristotle_input/`.
3. **`session-exit`** — выход из сессии по `TOOLS_SPEC.md` §5: состояние маршрута, журнал с
   `Boundary:`, kills через `kb.py add`, Spine, протокол, память, чистое дерево.

**Не skill, а починка данных:**

4. **Операторы** — перенести девять определений в `knowledge.db` (таблица `move` уже держит
   ходы с сигнатурой и статусом) либо в `CODEX_CONTROL` как раздел. Пока они в мёртвом
   документе, каждая ссылка `escape_operator: CertificateShift` — отсылка в никуда.
5. **Адресность oracle-вопросов** — единственная функция без замены. Либо оживить
   `oracle_questions.py` как есть, либо добавить в `knowledge.db` поле адреса и перенести.

**Ничего не удалять.** Всё вышеперечисленное — рабочие контуры, просто с разной степенью
заброшенности; решение о судьбе каждого принимает владелец.
